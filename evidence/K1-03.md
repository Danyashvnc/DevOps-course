# Работа K1-03

Группа: ИТ-9.24.2
Код студента: Danyashvnc

Что сделано: создал заявку, остановил api, посмотрел что происходит, нашёл причину по логам и статусу, запустил api обратно и создал новую заявку.

1. До сбоя. Открыл localhost:8080, отправил заявку "Не работает экран". Страница: "Заявка №1 принята", в списке 1 заявка. (скрин K1-03-1-zayavka1.jpg)

2. Остановил api:

```
docker compose stop api
```

Обновил страницу и список. Страница открывается, но пишет "Сервис заявок недоступен", счётчик пустой. (скрин K1-03-2-api-stopped.jpg)

3. Сравнил health и список:

```
curl -i http://localhost:8080/health
HTTP/1.0 200 OK
{"process": "running", "role": "web"}

curl -i http://localhost:8080/api/requests
HTTP/1.0 503 Service Unavailable
{"error": "upstream_unavailable", "request_id": "44b35828"}
```

4. Статус и логи:

```
docker compose ps -a
api   Exited (137) 19 seconds ago
web   Up (healthy)   127.0.0.1:8080->8000/tcp

docker compose logs --tail=20 web
{"time": "2026-11-07T00:00:19.446948+00:00", "role": "web", "event": "upstream_unavailable", "request_id": "44b35828", "target": "http://api:8000", "error": "<urlopen error [Errno -5] No address associated with hostname>"}
{"time": "2026-11-07T00:00:19.447054+00:00", "role": "web", ... "GET /api/requests HTTP/1.1\" 503 -"}
```

Гипотеза была: web работает, но не может достучаться до api. Подтвердилось: api в статусе Exited, web healthy, на список 503, а в логе web upstream_unavailable с адресом http://api:8000. request_id в логе тот же что в ответе curl.

Причина: остановлен api, web без него не может получить и сохранить заявки.

5. Восстановление:

```
docker compose start api
docker compose ps -a
api   Up 5 seconds (healthy)
web   Up (healthy)
```

6. Отправил новую заявку "Не заряжается" - "Заявка №2 принята", в списке обе, №1 и №2. (скрин K1-03-3-zayavka2.jpg)

```
api: {"event": "request_accepted", "request_id": 2}
web: "POST /api/requests HTTP/1.1" 201
```

Старая заявка не пропала, потому что данные лежат в томе requests, а stop/start его не трогает.

Ответ на вопрос (почему health у web остался успешным): /health у web проверяет только что сам процесс web запущен, к api он не обращается. web работал, поэтому 200. Что api упал, видно только по /api/requests (503) и по логам.
